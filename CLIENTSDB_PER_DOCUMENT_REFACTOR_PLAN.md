# clientsDb Per-Document Refactor — Scoping Plan

Companion to [data-loss-prevention-plan.md](./data-loss-prevention-plan.md) and [BACKUP_RESTORE_RUNBOOK.md](./BACKUP_RESTORE_RUNBOOK.md). Written Sep 2026, before any code changes, to size up the fix for the root cause behind both the original 1MiB-document incident and the save-conflict-banner annoyance: `clientsDb` bin-packs every client into a shared pool of Firestore documents instead of giving each client its own.

**This is a plan, not a change.** Nothing below has been implemented yet.

---

## The problem, restated precisely

`clientsDb` is one big in-memory JS object (`{ [clientName]: {...} }`), currently persisted across Firestore as `agency/clientsDb-shard-0`, `-1`, `-2`, ... via a greedy byte-size bin-packer (`packClientsDbIntoShards`, 700KB/shard cap, `app.js` ~line 5953). Two consequences fall directly out of that shape:

1. **Shared size ceiling.** No single client is guaranteed its own space. A client whose own data alone exceeds ~700KB rides through unsplit (this session's `findOversizedShards` guard, commit `745188d`, only catches this after the fact with a warning banner — it doesn't fix the underlying ceiling).
2. **Shared version/conflict scope.** All shards share one version counter (`agency/clientsDbShardMeta.version`). Any save anywhere — on *any* client — bumps it, so the save-conflict banner fires for everyone with the doc open, regardless of which client they're actually editing. Confirmed earlier this session: editing Client A and someone else saving Client B still triggers your conflict banner.

Both trace to the same root cause: clients share documents instead of each owning one.

## The target shape

One Firestore document per client, in a new top-level collection — `clientWorkspaces/{clientName}` — mirroring the pattern already proven safe in this exact codebase for Resource Booking Calendar (`resourceBookings/{bookingId}`) and Hours & Time Log (`hoursLogEntries/{entryId}`), both migrated off shared-document storage in Aug 2026 for the identical reason.

**Naming correction (caught before any code was written):** the obvious name, `clients/{clientName}`, collides with an *existing* `clients` collection already in production use for the public client portal (keyed by magic token, `allow get: if true` in `firestore.rules` - anyone holding a token can read their own doc, unauthenticated, by design). Putting private full client records in that same collection, even keyed by client name instead of token, would make every client's full internal data (proposals, contracts, notes, pricing) readable by anyone who could guess or enumerate a client name - client names are far less random than magic tokens. Using `clientWorkspaces` instead, matching the UI's own "CLIENT WORKSPACE" sidebar label, admin-only like `clientsDb` is today.

Critically, **the in-memory shape does not change.** `clientsDb` stays a single JS object indexed by client name, because that's what every call site already expects — see blast radius below. Only the persistence layer underneath it changes: instead of bin-packing the whole object into N shard documents, each client's slice gets its own document; instead of listening to shard documents, a live `onSnapshot` on the `clientWorkspaces` collection keeps the in-memory object in sync by merging individual doc add/modify/remove events.

This is the load-bearing design decision of this whole plan: it keeps the refactor scoped to the sync layer (a few functions in `app.js` and `_worker.js`) instead of touching the ~260 places across the codebase that read or write `clientsDb` as an object.

## Blast radius (confirmed by grep, not estimated)

- **`app.js`: 219 references to `clientsDb`**, including ~45 direct bracket-access reads/writes (`clientsDb[name]`, `clientsDb[activeClientName]`, etc.) scattered across dozens of features, not concentrated in one module.
- **41 other files** reference `clientsDb` — every tool that runs in an iframe (Hours Tracker, Proposal Calculator, Mood Board Builder, SEO Rank Tracker, and ~35 more), each reaching into `window.parent.clientsDb` directly.
- **`_worker.js`** independently re-implements the *entire* shard bin-packing scheme server-side (`firestoreGetDoc`/`firestoreSetDoc` against `agency/clientsDb-shard-N`, its own version-bump logic) for the Team-Access-restricted REST path. This is a second, separate implementation of the same logic that would also need to change.
- **`firestore.rules`** gates all of `clientsDb`/its shards with one coarse `hasAccountDataAccess()` predicate (all-or-nothing) — see lines ~196-197. The two existing per-document collections (`resourceBookings`, `hoursLogEntries`) are *not* actually a precedent for finer-grained per-record security — both just use `allow read, write: if isAdmin()`. True per-client Team-Access filtering at the rules level would be new, unproven territory here, not an established pattern.

**Conclusion:** if the in-memory shape is preserved (per the design decision above), the ~260 call sites across `app.js` and the 41 tool iframes need **zero changes**. The real work is concentrated in four places: the sync functions in `app.js`, the save function in `app.js`, the restricted-access path in `_worker.js`, and (optionally, see Phase 4) `firestore.rules`.

## What actually changes

1. **Read/sync (`app.js`):** Replace `startUnrestrictedClientsDbSync`'s shard-meta + shard listeners with one `onSnapshot` on the `clientWorkspaces` collection. On each snapshot's docChanges, `added`/`modified` events write `clientsDb[doc.id] = doc.data()`; `removed` deletes that key. Rebuild the dependent UI the same way it already does today after a shard update.
2. **Write/save (`app.js`):** `commitDatabaseToCloud` currently writes the *whole* `clientsDb` (repacked into shards) on every save. Change it to write only the *changed* client's document to `clientWorkspaces/{clientName}`. This requires tracking which client(s) actually changed since the last save — likely the simplest version is "whichever client is currently active," since nearly every write path already flows through `switchClient`/`activeClientName`. Needs a closer look during implementation for any code path that edits a non-active client's data (bulk operations, nudge checks that touch other clients' records) — those would need to loop and write each touched client's doc individually rather than relying on "just save the active one."
3. **Conflict detection:** Move from the single shared `clientsDbDocVersion` to a per-document version field (`clientWorkspaces/{clientName}.version`), compared only against that one client's fetched version before writing. This is what naturally fixes the cross-client false-conflict problem as a side effect, not a separate feature to build.
4. **Restricted (Team Access) path (`_worker.js`):** The REST endpoint's shard read/write logic needs the equivalent per-document rewrite. This is real, separate work — it's a different codebase (server-side REST calls, not client SDK) reimplementing the same bin-packing today, so it needs its own pass, not just a copy-paste of the `app.js` changes.
5. **`findOversizedShards` guard (commit `745188d`):** Becomes unnecessary post-migration — each client naturally gets Firestore's real ~1MiB ceiling instead of a shared 700KB packed-shard ceiling, and there's no more bin-packing to overflow. Can be removed once the migration is confirmed stable, not before.
6. **Backup paths:** `agency/clientsDbBackup-shard-*` (the app-level safety-net backup) and the Export/Import JSON format can both stay exactly as they are — they already operate on the in-memory `clientsDb` object as a whole, which is unaffected by this refactor. No changes needed there, which keeps the Step 3 test-restore work from this session valid without modification.

## What does NOT change

- The in-memory `clientsDb` object shape, and therefore all ~260 call sites across `app.js` and every tool iframe.
- Export Full Backup / Import Backups (operate on the in-memory object).
- The app-level shard backup mechanism (`clientsDbBackup-shard-*`) — separate concern, not urgent to migrate alongside this.
- The idle-lock and save-conflict-banner draft-restore features shipped this session (`50e3998`, `745188d`) — both key off the active client and DOM state, not the storage layer directly.

## Migration path

1. **One-time backfill script:** read the current shards (or call the existing `rebuildClientsDbFromShards`), write one document per client into the new `clientWorkspaces` collection. Verify count and a content diff against the source before treating it as done.
2. **Parallel-write period:** for a real stretch of time (a couple of weeks, not a couple of days, given this subsystem's history), write to *both* the old shards and the new per-client collection on every save, but keep reading from shards as the source of truth. This costs nothing but a few extra writes and gives a live, ongoing equivalence check with zero user-facing risk.
3. **Cutover:** switch reads to the `clientWorkspaces` collection listener. Keep the shard-write path active but dormant (or keep writing shards too, cheaply, as an extra safety net) for another stretch before removing it entirely.
4. **Legacy fallback:** keep a one-time migration read from the old shards, mirroring how `getLegacyClientsDbDocRef()` already handles the pre-sharding format today — so a Hub that somehow never got the new writes still self-heals on load.
5. **Rollback:** a simple flag to flip the sync path back to shards if anything looks wrong post-cutover, for as long as the shard data is still being kept current in parallel.

## Suggested phasing

- **Restricted-teammate read path — DONE, Sep 2026.** `_worker.js`'s `fetchAllClientsFromFirestore` (shared by 5 call sites: the restricted-data GET endpoint, the account-manager lookup, the Stripe subscription-deleted handler, the team workload view, and the health digest) now reads every document from `clientWorkspaces` via `firestoreListCollection` in one call, instead of walking shard indices. Old implementation kept intact as `fetchAllClientsFromShardsFallback`, used only if `clientWorkspaces` ever comes back completely empty. No `firestore.rules` change needed here - this is a service-account REST read, same as the Worker's other Firestore access, which bypasses rules entirely. This closes the gap left after the main cutover: restricted teammates' writes already landed in `clientWorkspaces`, but their reads still came from the (now-dormant-from-the-admin-side) shards until this.
- **Cutover — DONE (safer variant), Sep 2026.** Reads: `startClientWorkspacesSync` (new) replaces `startUnrestrictedClientsDbSync` (left intact, unused, as the one-line rollback) as what `loadDatabase()` actually calls - a single `onSnapshot` on the `clientWorkspaces` collection, no more per-shard partial-load race to guard against. Writes: `commitDatabaseToCloud` now writes one document per client to `clientWorkspaces` as the REAL, authoritative save - the old shard write is kept running too, but only as a dormant, non-version-checked rollback safety net. Deliberately did NOT implement true per-client conflict detection in this pass - `pendingLocalClientEdits` (the only candidate tracking mechanism already in this codebase) was confirmed NOT comprehensive during this same session (see its own comment and the notification-pile-up bug it was patched for), and getting that wrong risks silent data loss, a worse failure mode than today's false-positive conflicts. So this cutover keeps saving/conflict-checking the full client roster together, exactly like before - it fixes the Firestore size-limit problem immediately (each client now has its own ~1MiB ceiling, not a shared 700KB pool), but the cross-client false-conflict problem is still open, deferred to a separate, carefully-audited pass on per-client change tracking. Also required a real cross-cutting fix: `_worker.js`'s restricted-write endpoint had to start bumping the new `clientWorkspacesMeta` version counter too (previously only bumped the now-retired `clientsDbShardMeta`), or a restricted teammate's save could get silently overwritten by an admin's next full-roster save with no conflict ever surfacing - the exact bug the original shard-meta bump was written to prevent. `firestore.rules` also needed a new gate for `agency/clientWorkspacesMeta` (the browser SDK reads/writes it directly, unlike the Worker's service-account bypass).
- **Phase 1 — DONE (parallel-write only), Sep 2026.** `app.js`'s `commitDatabaseToCloud` now writes every client's data to `clientWorkspaces/{clientName}` alongside the real shard save, verified live: triggered a real save and confirmed all 6 clients (including Evry Intention LLC) got their own document. Reads, sync, and conflict-detection are untouched - still shard-based. Cutover has NOT happened yet; this is intentionally still just the parallel-write period.
- **Phase 2 — DONE (parallel-write only), Sep 2026.** `_worker.js`'s `handleRestrictedClientDataWrite` (the Team-Access-restricted REST path) now also writes to `clientWorkspaces/{clientName}` right after its real shard write, using the same raw REST `firestoreSetDoc` helper this file already uses elsewhere (not the browser SDK, since this runs server-side under a service-account token). No "which client changed" ambiguity here unlike Phase 1's app.js version - this endpoint is already scoped to exactly one client per call. Client names needed `encodeURIComponent()` before going into the raw REST URL path (`agency/clientsDb-shard-N` never needed this since shard indexes are just numbers) - free-text client names can contain spaces/parentheses/etc. that would otherwise break the URL. The Worker's write bypasses `firestore.rules` entirely (service-account access, same as its other writes), so no rules change was needed for this half.

**Observed during live Phase 2 testing (Sep 2026) - a real race, not a bug:** wrote a test value to a client's `meetingNotes` via the Worker endpoint, and on the first attempt it briefly showed up in `clientWorkspaces` then disappeared moments later - not silently dropped, but overwritten back out by that same open admin tab's own next full-roster parallel-write (Phase 1), which fired using an in-memory `clientsDb` snapshot captured before its per-shard listener had caught up with the Worker's just-written update. Confirmed self-correcting: an immediately-rechecked second write, and a delayed recheck of it, both held. This is the same listener-staleness race the "SECOND SAFETY NET" comment in `commitDatabaseToCloud` already documents and accepts for the real shard writes (a version-number match doesn't guarantee shard *content* has actually caught up) - not something this refactor introduces, just newly visible because nothing reads `clientWorkspaces` yet to mask a momentary mismatch. Low-stakes for exactly that reason during the parallel-write period; worth re-checking this doesn't matter once cutover makes `clientWorkspaces` the thing actually read from.
- **Phase 3 (optional/stretch)** — revisit `firestore.rules` to gate `clientWorkspaces/{clientName}` per-document instead of all-or-nothing, potentially simplifying or removing the custom REST endpoint entirely. Genuinely new territory for this codebase; worth its own separate scoping pass rather than bundling into Phase 1/2.
- **Phase 4 (optional)** — now that conflicts are per-client instead of global, the save-conflict banner's "hard-block-and-ask" UX could be revisited (e.g., a real-time merge might become safe when it wasn't before). Not assumed here — flagged only as something worth reconsidering once Phase 1 has been live for a while, not something to design now.

## True per-client conflict detection — audit findings and staged plan (Sep 2026)

Picking up the deferred work from the cutover: moving off the single global `clientWorkspacesMeta.version` check to real per-client conflict detection. Before writing any code, audited every place `clientsDb` gets mutated to check whether `pendingLocalClientEdits` (the only existing "which client(s) actually changed" tracking mechanism) is comprehensive enough to build on. It is not, confirming the concern already on record above. Full findings below; nothing in this section has been implemented yet.

**Why this matters more than it might look like it should:** today, `commitDatabaseToCloud` writes *every* client's document on *every* save, unconditionally (`Object.entries(cleanDb).map(...)`), regardless of what `pendingLocalClientEdits` contains — that set is bookkeeping only right now, not a write filter. So today, a gap in `pendingLocalClientEdits` costs nothing for unrestricted admins (the full write covers everyone anyway). But the Worker's restricted-teammate write path (`handleRestrictedClientDataWrite` / `commitRestrictedClientEditsNow`) **already** scopes its writes strictly to `pendingLocalClientEdits` — so every gap found below is a **live bug today** for restricted teammates, independent of anything else in this plan. And building true per-client conflict detection *requires* moving admin writes to the same scoped-write model too (checking a per-client version only makes sense if you're not about to blindly overwrite every other client's doc with a possibly-stale in-memory copy regardless of what that check says) — so `pendingLocalClientEdits` has to become fully comprehensive before that move is safe, or a real edit to a non-active client could go from "saved, but with a false-positive conflict banner sometimes" (today) to "silently never reaches the cloud at all" (worse).

**Confirmed gaps** (full audit, both self-verified and agent-assisted, cross-checked against the actual code):

1. **Bulk Import Backups** (`app.js` ~line 5795-5798) — `clientsDb = {...clientsDb, ...importedClients}; saveDatabase();` fires *before* `activeClientName` is reassigned, so none of the imported clients (could be all 6) get stamped. Same flow exercised live during this session's Step 3 test-restore.
2. **`createNewClient()`** (~line 1650) — `saveDatabase()` fires one line before `activeClientName` is set to the new client's name; the new client is never stamped.
3. **`backfillMissingClientChecklists()`** (~line 6122, called from inside `saveDatabase()` itself at line 6150, and again from `loadDatabase()` at boot) — loops every client missing `clientChecklist` and backfills it, but only `activeClientName` gets stamped by the save that follows. Runs on *every* save, so this silently rides along with all 20 `saveDatabase()` call sites.
4. **`migrateSchemaAndDefaults()`** (~line 1502, called once from `loadDatabase()` at boot) — loops every client, migrates schema/defaults, and does not call `saveDatabase()` or touch `pendingLocalClientEdits` at all. Worst of the group: zero protection for any client it touches until some unrelated save happens to cover it.
5. **`syncContractRenewalDateToRenewalTracker(clientName, ...)`** (~line 4897) — explicit cross-tool bridge (Contract & Invoice Tracker writing into a different client's renewal-tracker fields), mutates a parameter-supplied client name, never stamps it.
6. **`createClientDriveFolder(name)` / `createClientClickUpFolder(name)`** (~lines 7601, 7626) — async fire-and-forget; if the admin switches active client while the `await fetch(...)` is in flight, the eventual save stamps the *new* active client instead of `name`.
7. **`resetSandboxBtn` handler** (~line 1103) — hardcoded `clientsDb["Quick Sandbox (One-Offs)"]` mutation with no check that the sandbox is actually the active client.

Also confirmed **not** a gap: the client-portal `onSnapshot` fold-in (~line 9115) already explicitly stamps; `renameActiveClient`/`deleteActiveClient` both reassign/retain `activeClientName` before their save so they're covered (deletion still needs `intentionallyRemovedClientNames`-aware handling downstream, which already exists); no `postMessage`-based iframe dispatcher exists in this codebase (tools call `window.parent.<fn>` directly instead) — `pushClientNotification` is the one parent-exposed function that mutates a caller-supplied client without stamping it itself, but it doesn't call `saveDatabase()` internally, so responsibility sits with whichever iframe tool calls it (not audited in this pass — flagged as a follow-up if any tool iframe turns out to call it for a non-active client).

**Proposed staged plan:**

- **Stage 1 (safe, additive, do first):** Add explicit `pendingLocalClientEdits.add(name)` stamps at all 7 confirmed gap sites above, matching the existing pattern already used for the portal fold-in fix. Zero behavior change for unrestricted admins (writes are still full-roster). For restricted teammates, this is a straight bug fix — more gets sent, never less. Low risk, independently valuable regardless of whether Stages 2+ ever happen.
- **Stage 2:** Add a per-client version field on each `clientWorkspaces/{clientName}` document (or a lightweight sibling `_version` field), bumped on every write to that specific document — both from `app.js` and from the Worker's restricted-write path (which currently does no conflict check at all on that path, just a read-modify-write with a small acknowledged race window — see `handleRestrictedClientDataWrite`'s own comment).
- **Stage 3:** Switch `commitDatabaseToCloud` from "write every client, check one global version" to "write only `pendingLocalClientEdits` (+ `intentionallyRemovedClientNames` for deletes), each checked against its own fresh per-client version right before writing." This is the actual fix for the cross-client false-conflict problem — and only becomes safe once Stage 1 has closed every gap, per the reasoning above.
- **Stage 4:** Give the Worker's restricted-write path the same real per-client version check (today it has none).
- **Stage 5:** Live verification pass — the same "two tabs, deliberately simulate a conflict" testing style already used for the global check during the cutover, but now confirming (a) editing different clients truly no longer cross-triggers the banner, and (b) a real same-client conflict is still caught reliably.

Each stage gets its own commit, push, `verify-hub.js` pass, and live check before moving to the next — same discipline as every other phase in this document.

**Stage 2 — DONE (parallel-tracking only, not yet used for conflict decisions), Sep 2026.** Each `clientWorkspaces/{clientName}` document now carries its own `_clientDocVersion` field (constant `CLIENT_DOC_VERSION_FIELD`, defined identically in both `app.js` and `_worker.js`), bumped by 1 on every write to that specific document - by `commitDatabaseToCloud` (admin path) and by `handleRestrictedClientDataWrite` (restricted-teammate path, which now reads the client's current version fresh right before writing, rather than assuming it knows it). Tracked client-side in a new, deliberately separate `clientWorkspaceVersions` map (name -> version) rather than as a field inside `clientsDb[name]` itself - `clientsDb`'s in-memory shape is read by ~260 call sites (exports, restricted-field-diffing, schema migration, every tool iframe) that should never see an internal bookkeeping field. `startClientWorkspacesSync`'s snapshot handler strips the field out of what lands in `clientsDb` and records it into the separate map instead (skipping updates from a pending/unconfirmed echo, mirroring the data-echo-skip fix from the regression above). Server-side, `fetchAllClientsFromFirestore` strips the field before returning to ANY of its 5 callers - critical because the restricted-data GET endpoint's response gets assigned wholesale into a teammate's `clientsDb` with no stripping on that side, so leaving it in would have polluted every restricted teammate's local copy and their own field-diffing logic. While making this change, also found and documented (not yet fixed - flagged for Stage 4) that `handleRestrictedClientDataWrite`'s own comments were stale post-cutover: the shard write it still treats as "the real save" is actually the dormant one now, and the clientWorkspaces write that actually matters is wrapped in a try/catch that reports success even if that specific write fails. Deliberately NOT yet used for any conflict-check decision anywhere - this stage only gets real per-client version numbers flowing and verified live first, matching the same parallel-period discipline already used for `clientWorkspaces` itself before its own cutover.

**Stage 3 design (Sep 2026, not yet implemented) - proposed approach:**

1. Write only `Array.from(pendingLocalClientEdits)` (+ explicit deletes for `intentionallyRemovedClientNames`) instead of every client in `cleanDb`. This is the actual scoping change.
2. Before writing, fetch each pending client's `clientWorkspaces/{name}` doc fresh and compare its `_clientDocVersion` against this tab's last-known `clientWorkspaceVersions[name]`. All-or-nothing: if ANY pending client fails its check, reject the WHOLE save (same hard-block-and-ask simplicity as today, just now naming the specific conflicting client(s) in the banner instead of vaguely blaming "the client database"). No partial saves - keeps the "someone else saved, reload and redo" mental model intact everywhere else in the Hub already uses it.
3. Retire the GLOBAL `clientsDbDocVersion`/`clientWorkspacesMeta.version` check as the gating mechanism (superseded by per-client checks) - but per this codebase's own established rollback discipline, keep the meta doc's listener and bump running, unused, rather than deleting it. It was always somewhat redundant with the live collection listener anyway (admin tabs learn about changes from the collection snapshot directly, not from the meta bump); keeping it costs nothing and preserves a one-line rollback (point the gate back at the global check) if Stage 3 needs to be reverted.
4. The old "SECOND SAFETY NET" stale-tab guard (refusing to save if the cloud has a client name this tab doesn't know about) becomes logically unnecessary once writes are scoped - it existed specifically to catch a stale FULL-ROSTER write silently deleting-by-omission a client the tab never knew existed. Under scoped writes, an unknown client is simply never touched at all, so that failure mode can't happen. Proposed: keep the check running but stop letting it BLOCK saves (log-only) for one verification stretch, then remove it once confirmed genuinely dead, rather than deleting it in the same commit that changes the write scope.

Given this is the first Stage in this whole refactor that changes actual admin save BEHAVIOR (not just parallel bookkeeping), asking before implementing rather than after, matching how the original cutover itself was gated.

**Stage 3 — DONE (implemented as designed), Sep 2026.** `commitDatabaseToCloud` now writes only `namesToWrite` (the clients actually in `pendingLocalClientEdits`, filtered to ones that still exist) instead of every client in `cleanDb`. Before writing, fetches each pending client's own document fresh and compares its `_clientDocVersion` against this tab's last-known value (`clientWorkspaceVersions`); a mismatch on any pending client rejects the whole save (all-or-nothing, same hard-block-and-ask shape as before) and the banner now names the specific conflicting client(s) instead of vaguely blaming "the client database." The old global `clientsDbDocVersion`/`clientWorkspacesMeta.version` check no longer gates anything - the meta doc is still bumped on every successful save (cheap, and preserves an instant one-line rollback to global gating if needed), just not read-and-compared beforehand anymore. The size guard is scoped to `namesToWrite` too. The "SECOND SAFETY NET" stale-tab guard (previously blocking) is downgraded to log-only, per this stage's design note above - its original failure mode (a stale full-roster write silently deleting-by-omission an unknown client) can't happen once writes are scoped, but it's kept as a signal for a verification stretch rather than removed outright in the same change. Deletions (`intentionallyRemovedClientNames`) are NOT yet covered by the per-client version check - still sent unconditionally, flagged as a reasonable small follow-up rather than folded into this pass. The backup write, dormant shard safety-net write, and `syncPublicPortalDocs` all deliberately remain scoped to the FULL `cleanDb`, not `namesToWrite` - unchanged, since they each have their own reasons to want the complete picture regardless of what this particular save's real write touches.

**Stage 1 + Stage 2 live verification (Sep 2026) - PASSED.** After pushing/deploying both stages together: confirmed `clientWorkspaceVersions` populates correctly on load with no leak into `clientsDb`; a real write through the restricted-write REST endpoint bumped only the targeted client's version (0→1) and left every other client's version untouched; a real admin save via `saveDatabase()` bumped every client's version by exactly 1 (full-roster write, as expected pre-Stage-3), including correctly picking up the restricted endpoint's prior bump (1→2 for that client); the restricted-data GET endpoint's response was confirmed to never include `_clientDocVersion` for any client; zero console errors. One transient false-negative during testing (a `saveDatabase()` call landing in a narrow window right after reload logged "clientWorkspaces hasn't finished its first sync yet" despite `clientWorkspacesSyncReady` reading `true` moments before/after) self-resolved on retry and wasn't reproduced again - noted, not treated as a real issue, but worth keeping an eye on if it recurs.

**Stage 1 — DONE, Sep 2026.** All 7 confirmed gaps closed with explicit `pendingLocalClientEdits.add(name)` stamps: bulk import (stamps every imported client name, not just the one `activeClientName` happens to land on), `createNewClient`, `backfillMissingClientChecklists` (now stamps per-client instead of relying on the caller), `migrateSchemaAndDefaults` (now also returns whether anything changed, and `loadDatabase()` triggers a save if so - previously this ran at boot and never pushed its backfilled defaults to the cloud at all), `syncContractRenewalDateToRenewalTracker`, `createClientDriveFolder`, `createClientClickUpFolder`, and `resetSandboxBtn`. Zero behavior change for unrestricted admins today (writes are still full-roster, pending Stage 3) - purely additive bookkeeping that becomes load-bearing once Stage 3 scopes writes. For restricted teammates, this is a live bug fix: their write path already scopes to `pendingLocalClientEdits`, so these gaps were previously causing real, silent under-sends for anything the schema-migration/backfill passes touched.

**Urgent regression fix (out of band, Sep 2026) — DONE.** While doing the audit above, found that `startClientWorkspacesSync` (the live sync listener since the cutover) was missing every protection the old `rebuildClientsDbFromShards` it replaced had: no `hasPendingWrites` echo-skip, no `pendingLocalClientEdits` merge-back over the incoming snapshot, and no `skipActiveIframeReload` on its `refreshAllViews()` call. Net effect: any admin or restricted teammate saving *anything*, for *any* client, could silently overwrite every other open tab's in-memory `clientsDb` wholesale — discarding another tab's still-typing, not-yet-confirmed edit to a totally unrelated client, and re-triggering the previously-fixed (Aug 2026) forced-iframe-reload glitch. This is the exact failure mode behind both real prior data-loss incidents, introduced as a straight regression by this session's own cutover work, not a pre-existing issue. Fixed immediately (commit `e490e17`, ahead of the staged plan above given the severity) by mirroring `rebuildClientsDbFromShards`' proven pattern. Verified live: simulated an in-flight, unsaved edit to one client, then triggered a genuine out-of-band Firestore write to a *different* client via the restricted-write REST endpoint (bypassing this tab's own save pipeline entirely, to simulate another admin saving something unrelated) — confirmed the in-flight edit survived the resulting collection snapshot instead of being clobbered. Test state cleaned up afterward without ever persisting the test value.

## Risk notes specific to this codebase

Two real client-data-loss incidents (Reginald White, Evry Intention LLC) are the reason this subsystem gets extra caution. Recommend:

- No phase ships without `node scripts/verify-hub.js` passing clean, same as every other change this session.
- The parallel-write period is not optional — it's the cheapest possible insurance against a subtle bug in the new per-document write/merge logic, and costs nothing but a few extra Firestore writes per save.
